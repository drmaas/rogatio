## Implementation strategy

TDD

## Goal

When the Sample Rules Group is active and its declared origins are granted, the two header rules (`grp-sample/rule-header-set`, `grp-sample/rule-header-remove`) must report `active` instead of `error`, because their DNR installation actually succeeds. When a header rule genuinely fails to install, the management page must tell the user why: the `error` word in the rule status list becomes an activatable control that navigates to the failing rule in the workspace editor and focuses its card, and a distinct error card renders the concrete failure reason (Chrome's own `updateDynamicRules` message, carried today in `extension.dnr-error` `params.reason`) as plain text with a deterministic fallback. Both halves are needed: the first removes the false `error`, the second makes any remaining real `error` explainable instead of a dead red word.

## Non-goals

- **Not** changing what `error` means in `packages/browser-core`. `computeRuleStatuses` keeps its single definition — enabled, permitted, and absent from `installedRuleIds` (`packages/browser-core/src/status.ts:62-74`). Header rules read `active` because their ids genuinely enter `installedRuleIds`, never because the status is special-cased.
- **Not** removing the redirect/query masking at `packages/extension/src/service-worker.ts:198-205` (research Q2). That inverse bug — a failed redirect/query install reported as `active` with diagnostics discarded — stays as-is and is recorded as a follow-up.
- **Not** changing the popup (research Q3). `packages/extension/src/popup.ts` keeps rendering `statusLabel(row.status)` only; no error link, no error card, no diagnostics.
- **Not** installing header rules one call per rule (research Q4). The single batched `updateDynamicRules` call stays; error attribution stays batch-wide.
- **Not** wiring the header field extension (`packages/editor/src/rule-types/header.ts`) into the management page's `createEditor` call (research Q5). The rule card is the navigation target; header-specific controls remain absent and are recorded as a follow-up.
- **Not** widening `EditorController`'s public boundary with a rule-scoped navigation method (research Q6), unless Phase 4 proves host-side navigation plus DOM focus insufficient — in which case the work stops at the gate rather than widening silently.
- **Not** adding new diagnostic codes, new message commands, or new payload fields. No new browser-core exports, no schema change, no compiler change.
- **Not** reworking the attention note, the badge pill, or `ATTENTION_PRECEDENCE`. Their canned text is unchanged and their existing test hooks stay.
- **Not** fixing DNR id collisions across projects or the repeated `installHeaderRules` call on every state computation. Both are pre-existing and recorded as risks.

## Architecture

**Two independent defects, two independent fixes, one shared package.** Everything lands in `packages/extension`; no other package changes. That keeps the documented dependency direction untouched and honours the constraint that Chrome-specific error text is attached in the extension, not in browser-core.

**1. Make the emitted DNR rule acceptable to Chrome (`packages/extension/src/installer.ts`).**
`toDnrRule` emits two defects that a real Chrome `updateDynamicRules` call can reject while every existing mock accepts:

- Both modify-header lists are always present, so one is necessarily an empty array (`packages/extension/src/installer.ts:100-110`). A request-direction rule ships `responseHeaders: []`; a response-direction rule ships `requestHeaders: []`.
- `condition` keys are written with the literal value `undefined` rather than omitted (`packages/extension/src/installer.ts:112-128`).

The fix is conditional-spread omission in both places, matching the pattern already used for `value` in `toDnrHeaderAction` (`packages/extension/src/installer.ts:84-92`) and for the matcher in `projectHeaders` (`packages/extension/src/projection.ts:269-277`). `DnrHeaderRule.action.requestHeaders` / `responseHeaders` become optional properties. Rationale: the repository already has a precedent where Chrome rejected a present-but-undefined property and the fix was omission, with the rejection recorded as the test's rationale (`packages/extension/test/permission-grant.test.ts:305-314`).

Because the empty-list hypothesis is a hypothesis, Phase 1 obtains real evidence before Phase 2 claims a fix. The evidence vehicle is a real-Chromium Playwright spec in the style of `test/browser/extension-real.spec.ts`: it loads the built extension, and from an extension page (which holds the `declarativeNetRequest` permission per `packages/extension/public/manifest.json:14`) calls `chrome.declarativeNetRequest.updateDynamicRules` with the exact object literal `toDnrRule` produces for each sample header rule, capturing accept or reject. Adding a dynamic rule does not require host permissions — only matching does — so this probe works without the un-automatable optional-permission prompt.

**2. Surface the reason that already reaches the page (`packages/extension/src/extension-page-entry.ts`).**
No new plumbing is needed. `operationStatuses` already replaces `core.rule-not-installed` with `extension.dnr-error` carrying `params: { ruleId, reason }` when a header install error matches an `error` status (`packages/extension/src/service-worker.ts:133-146`), and the header branch passes non-`active` statuses through unchanged (`packages/extension/src/service-worker.ts:188-197`). The page receives them as `Record<string, unknown>` (`packages/extension/src/extension-page-entry.ts:27`) and throws them away in the status list loop (`packages/extension/src/extension-page-entry.ts:438-448`).

The page gains one private narrowing reader that walks `unknown → diagnostics array → diagnostic record → params.reason`, returning the diagnostic code plus optional reason and stable message. It prefers `extension.dnr-error`, then uses the first usable diagnostic. Rationale for narrowing at the page rather than declaring a shared type: the payload crosses a `chrome.runtime.sendMessage` boundary and is untrusted structured data by repository rule; a declared type would assert a shape the page cannot verify. The reader uses own-property checks and tolerates malformed records or throwing accessors without taking down the page. The stable user-facing identity is `diagnostic.code`; `params.reason` is variable third-party detail, so absence of `reason` falls back to the diagnostic's own stable `message`, and absence of both falls back to a page-owned constant string.

**Rendering (research Q7 — one card).** The status list item keeps its exact current text (`${groupId}/${ruleId}: ${statusValue}`) so existing coverage on `[data-rule-statuses]` keeps matching. For `error` only, the status word is rendered as a `<button type="button">` carrying `data-rule-error-link`, `data-group-id`, and `data-rule-id`, with an accessible name that names the rule. A button, not an anchor: the action is in-page state change plus focus, there is no navigable URL, and the page's existing delegated `click` handler on the shell already dispatches on `dataset` (`packages/extension/src/extension-page-entry.ts:783-820`), which gives keyboard activation for free.

Exactly one error card renders, keyed by a module-level selected `{ groupId, ruleId }` pair (the same pattern as `activeTab`, `pendingProjectId`, `diagnosticsOpen` at `packages/extension/src/extension-page-entry.ts:66-91`). A pair is required because rule ids need not be unique across groups. With no valid selection it shows the first `error` status in payload order; activating a link selects that rule. If refreshed state removes the selected error, rendering falls back to the first current error; with no current errors, no card renders. The card describes only the selected rule. It does not group statuses merely because Chrome returned equal message strings: batch attribution is already imprecise, and message equality is not a sound failure identity. The card follows the existing distinct-card precedent — `.rogatio-runtime-guidance` with a `.rogatio-runtime-guidance-error` line (`packages/extension/src/extension.css:309-328`) as rendered at `packages/extension/src/extension-page-entry.ts:734-746` — with its own `rogatio-rule-error-card` class and `data-rule-error-card` hook, so no existing style or test hook is repurposed. The reason is assigned via `textContent` only, never `innerHTML`, keeping the page's existing construction style.

**3. Navigation and focus (research Q6 — host-side).** Activating an error link sets `activeTab = "workspace"`, sets the selected error rule, re-renders, then calls `editor.navigateToGroup(groupId)` and focuses `document.getElementById(\`rogatio-rule-${groupId}-${ruleId}\`)`. This mirrors, from the host side, exactly what the editor already does internally for search-result jumps — `render()` then `getElementById` then `scrollIntoView` then `focus({ preventScroll: true })` (`packages/editor/src/editor.ts:1764-1775`) — and relies on `navigateToGroup` rendering synchronously (`packages/editor/src/editor.ts:1733-1747`). `getElementById` with the raw id avoids selector escaping and selector injection entirely; no CSS selector is built from project data. The editor is only mounted on the workspace tab with at least one project (`packages/extension/src/extension-page-entry.ts:886-932`), which is exactly when the sidebar and its status list exist, but the handler still guards `editor` being undefined and the card being absent.

**Test strategy.** Real Chrome validation goes in `test/browser/` (real-extension context). Emitted-shape and payload contracts go in `packages/extension/test/` (Vitest). Rendering, keyboard activation, navigation, focus, and text-not-HTML go in `test/browser/extension.spec.ts`, whose existing mocked-`chrome` `addInitScript` harness already lets a test inject `ruleStatuses` with arbitrary `diagnostics` plus a project with groups and rules so the editor mounts (`test/browser/extension.spec.ts:437-505`). `pnpm validate` runs typecheck, Vitest, and Playwright (`scripts/validate.ts:32`, `:425`, `:441`), so all three layers are in the canonical gate.

**Public API and wire-format changes (explicit).**

- `DnrHeaderRule` (exported from its source module but not from the package entry point): `action.requestHeaders` and `action.responseHeaders` change from required to optional; several `condition` keys stop being emitted as present-with-`undefined`. This is not a package public-API change, but it changes the wire object handed to Chrome and may affect direct internal imports and tests.
- No change to `ExtensionDiagnosticCode`, `extensionDiagnostic`, `RuleStatus`, `RuleStatusInput`, `computeRuleStatuses`, `computeBadge`, `EditorController`, or any message command or response envelope.
- New page-internal contract made load-bearing: the page now depends on `ruleStatuses[].diagnostics[].code` and `.params.reason` as produced by `operationStatuses`. Both sides live in `packages/extension`; the dependency is pinned by a service-worker test so a future change to the enrichment cannot silently blank the card.
- New DOM/CSS contracts: `[data-rule-error-link]`, `[data-rule-error-card]`, and `.rogatio-rule-error-card`. Preserved unchanged: `[data-rule-statuses]` item text format, `.rogatio-attention-note`, `[data-badge-state]`, `[data-runtime-guidance]`.

## Phases

### Phase 1 — Establish the real Chrome rejection (evidence only)

Add a real-Chromium Playwright spec that loads the built extension the way `test/browser/extension-real.spec.ts:7-25` does, opens an extension page, and calls `chrome.declarativeNetRequest.updateDynamicRules` with the exact object literals `toDnrRule` currently produces for `rule-header-set` (request direction, so `responseHeaders: []`) and `rule-header-remove` (response direction, so `requestHeaders: []`), including the `condition` keys currently emitted with `undefined`. If real Chromium cannot run, this phase is blocked; the plan does not claim or ship an unverified root-cause fix.

Acceptance: the spec runs in the repository's real-Chromium harness and produces a recorded accept/reject outcome per sample header rule, with any rejection message copied into the workflow log. Tests proving it: the new real-extension spec itself, executed via `pnpm test:browser`.

## Risks

- **The root cause is a hypothesis until Phase 1 lands.** The always-present empty opposite-direction array is the leading candidate, but `regexFilter` constraints, `initiatorDomains` semantics for a group-origin XHR rule, `priority` bounds, or DNR id collisions are all live alternatives. If Phase 1 shows Chrome accepting the current shape, Phase 2 is mis-scoped and must be re-planned at the gate rather than patched.
- **Real-Chromium evidence may be unobtainable in the reported environment.** The probe needs a built `packages/extension/dist` and a working Chromium; if it cannot run, implementation stops at the gate because the plan cannot establish or regress the claimed root cause.
- **The full end-to-end path cannot be proven in a real browser.** Header projections are filtered to granted origins before install (`packages/extension/src/service-worker.ts:309-315`), and the optional host-permission prompt is deliberately not automated (`test/browser/extension-real.spec.ts:79-84`). "Header rules read `active`" is therefore proven with mocked permissions in Vitest plus real Chrome acceptance of the rule shape, not by one real end-to-end journey.
- **Q2 deferral leaves an inverse bug in place.** Redirect and query rules whose install failed still report `active` with diagnostics discarded (`packages/extension/src/service-worker.ts:198-205`). A user could see a green redirect rule that is not installed, which is the mirror image of the reported complaint. Follow-up only.
- **Q4 batch attribution can blame a healthy rule.** One rejected rule in the batch marks every submitted header rule failed with the same message (`packages/extension/src/installer.ts:180-190`), so each selected rule's card may display a batch reason caused by another rule. Accepted for now; card copy must describe a reported batch install failure rather than claim that Chrome identified this rule as the cause.
- **Q5 lands the user on a card without header controls.** The management page supplies redirect, mock, and response-body rule types only (`packages/extension/src/extension-page-entry.ts:888-896`); the header field extension exists but is not built in (`packages/editor/src/rule-types/index.ts:11-16`). Navigation therefore reaches the right card with only common matcher fields — better than today's dead red word, but not a fix for the header rule itself. Follow-up.
- **Scope discipline.** Chrome messages are rendered without new truncation or rewriting; no per-status cosmetic classes, generic diagnostics utility, new module, configuration, diagnostic code, or message command is added. The one narrowing reader stays private in `extension-page-entry.ts`.
- **Untrusted third-party text and structure.** Chrome's message is external input rendered in the page. `textContent` only, never `innerHTML`, with an explicit test that markup in the reason stays literal. The narrowing reader must use own-property reads and tolerate non-array `diagnostics`, non-object entries, inherited fields, throwing accessors, and non-string `reason` without throwing or invoking inherited behavior.
- **Focus timing.** The plan depends on `navigateToGroup` rendering synchronously (`packages/editor/src/editor.ts:1733-1747`). If a future editor change makes rendering async, host-side focus silently stops landing; the browser test asserting `activeElement` is the guard.
- **Existing coverage depends on list text.** `test/browser/extension-real.spec.ts:70-72` matches `needs permission` inside `[data-rule-statuses] li`. Wrapping the status word in a button must not change `textContent`.
- **Pre-existing performance and correctness issues left untouched.** `installHeaderRules` runs on every state computation (`packages/extension/src/service-worker.ts:305-334`), re-issuing `updateDynamicRules` on every refresh; a failed `getDynamicRules` silently skips removals (`packages/extension/src/installer.ts:162-172`); `projectHeaders` assigns ids as `2_000_001 + index` per project (`packages/extension/src/projection.ts:266`), so two projects can collide in the same dynamic rule space. Out of scope, recorded so the next reader knows they were seen.
- **Security posture unchanged.** No new permission, no new host access, no new network call, no new storage key. The only new trust surface is rendering an external string as text.

## Acceptance criteria

1. With a resolving DNR mock, an active `grp-sample`, and its declared origins granted, `grp-sample/rule-header-set` and `grp-sample/rule-header-remove` both report `status: "active"`, and no `error` status appears for them.
2. `toDnrRule` for a request-direction projection produces an object with no `responseHeaders` key; for a response-direction projection, no `requestHeaders` key; and in neither case does any `condition` key exist with the value `undefined`.
3. Real Chromium accepts `chrome.declarativeNetRequest.updateDynamicRules` for the corrected shape of both sample header rules, and Chrome's rejection message for the pre-fix shape is recorded verbatim in the workflow log (or the phase records that the pre-fix shape was accepted, forcing a re-scope).
4. A thrown header-install failure surfaces in the page payload as `status: "error"` with `diagnostics[0].code === "extension.dnr-error"` and `params.reason` equal to the thrown message; a non-`Error` rejection yields the stable fallback message instead.
5. On the management page workspace view, every `error` status renders its status word as a keyboard-focusable, keyboard-activatable control whose accessible name identifies the group and rule, while each list item's text still reads exactly `groupId/ruleId: status`.
6. Exactly one error card is rendered at a time. It shows the reason and group/rule identity for the selected failed rule, defaults to the first `error` status when no valid selection exists, falls back when selected status disappears, and is absent when there are no current errors. Equal reason strings do not merge distinct statuses.
7. Reason resolution degrades deterministically: `params.reason` when present, otherwise the diagnostic's stable `message`, otherwise a page-owned constant. Markup inside a reason renders as literal text and creates no element.
8. Activating an error link switches to the workspace tab, navigates the editor to the failing rule's group, and leaves focus on `#rogatio-rule-<groupId>-<ruleId>`; when the group or card cannot be found, the card subject still updates and no uncaught error occurs.
9. No CSS selector is built from project-supplied ids; rule-card lookup uses `document.getElementById`.
10. `packages/browser-core`, `packages/compiler`, `packages/schema`, `packages/editor`, `packages/cli`, `packages/runtime`, and `packages/dry-run` are unchanged; the popup is unchanged; `packages/extension/src/service-worker.ts:198-205` is unchanged.
11. Malformed diagnostics, inherited diagnostic fields, and throwing accessors do not throw or execute inherited behavior; existing hooks keep working: `[data-rule-statuses]`, `.rogatio-attention-note`, `[data-badge-state]`, `[data-runtime-guidance]`, and the assertions at `test/browser/extension.spec.ts:421-433`, `:497-504`, and `test/browser/extension-real.spec.ts:68-72`.
12. `pnpm validate` passes, and the recorded evidence maps each criterion above to the test that proves it.
